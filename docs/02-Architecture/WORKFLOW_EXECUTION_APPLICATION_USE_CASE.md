# Phase 3 — Workflow Execution Application Use Case

Status: Design baseline
Date: 2026-09-18
Issue: #40

## Purpose

Define the first concrete application use case that turns a persisted Workflow definition into a runtime Execution. This establishes the orchestration boundary before adding another implementation increment.

## Committed Decisions

### 1. The application layer starts an Execution from a published Workflow

The use case accepts a Workflow identity and resolves the Workflow through WorkflowRepository.

Execution may only be created for a published Workflow. Draft definitions are authoring state and are not executable runtime input.

### 2. Workflow remains definition; Execution remains runtime

The use case does not copy workflow lifecycle into Execution and does not mutate the Workflow while starting execution.

Execution owns runtime state such as current step, attempt, and lifecycle timestamps.

### 3. Start persistence is explicit

The initial application flow is:

1. load Workflow;
2. reject missing Workflow;
3. reject non-published Workflow;
4. create Execution from the Workflow identity;
5. persist the new Execution;
6. start the Execution;
7. persist the updated Execution;
8. return the Execution.

The exact ordering of create/start persistence is an implementation detail to be covered by TDD, but the resulting contract is that a successfully started execution is durably represented as RUNNING.

### 4. Orchestration belongs in the application layer

The use case coordinates repositories and domain behavior. It does not implement Workflow invariants, Execution state transitions, capability provider logic, or persistence mechanics.

### 5. Capability execution is not part of the first start use case

Starting an Execution and executing its first capability are separate concerns. The first use case establishes runtime creation and lifecycle persistence without prematurely coupling it to provider execution.

A later execution-step use case may resolve the current WorkflowStep and dispatch its capability through the existing CapabilityDispatcher.

### 6. Failure boundaries are explicit

Expected domain/application failures include:
- Workflow not found;
- Workflow not published;
- repository failures propagated without being converted into provider errors.

No generic catch-and-wrap behavior is introduced until an actual application error contract requires it.

### 7. Execution identity is generated by the domain

The application use case calls Execution.create(workflow.id). It does not generate or inject the Execution UUID.

## Deferred Scope

- execution of WorkflowStep capabilities;
- conditions and condition evaluation;
- scheduling/background workers;
- durable ExecutionContext;
- transaction/Unit of Work abstraction;
- production database adapter;
- event publication;
- retries at the application orchestration boundary beyond the existing Execution retry state machine.

## Design Consequence

The first executable application boundary is intentionally narrow: create and persist a runtime Execution for a published Workflow. This gives the project a concrete use case against which repository contracts and domain lifecycle rules can be tested without choosing infrastructure technology.

## Gate Result

The application boundary is sufficiently defined for a TDD implementation increment.
